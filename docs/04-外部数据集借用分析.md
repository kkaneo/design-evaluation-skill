# 外部数据集借用分析：UXBench / WiserUI-Bench / ml-rldf

> 目的：评估三个开源仓库的数据能否借入 design-evaluation-skill，解决当前"评审依据薄、输出无金标准校准、E1 硬检查缺失"的问题
> 分析日期：2026-11-03（基于各仓库 README 与论文公开信息）

---

## 0. 为什么当前 skill 会显得"鸡肋"

三个根因，恰好对应三个数据集的药方：

| 病根 | 表现 | 药方 |
|---|---|---|
| 评审依据薄 | 条目只有文献主张，无真实案例支撑，AI 说"可能增加查找成本"时没有任何实证锚点 | **WiserUI-Bench**：300 对真实 A/B 测试 + 专家解释 |
| 输出无金标准 | Issue 记录格式是我们自己设计的，没有对照过"专家实际怎么表述设计问题" | **ml-rldf**：21 位设计师约 1500 条带锚点的批评标注 |
| E1 硬检查缺失 | 全部条目都靠模型 E2 推断，没有"可确定性判定"的机器检查项 | **UXBench**：8 类视觉证据可判定的缺陷任务 + 开源 4B 诊断模型 |

## 1. 三仓库概览

| 维度 | UXBench (afx-team/UI-UX) | WiserUI-Bench | ml-rldf (Apple) |
|---|---|---|---|
| 出处 | 蚂蚁集团，CVPR 2026 Findings | KAIST 等，ACL 2026 | Apple AIML，arXiv 2509.16779 |
| 数据规模 | 2,000 VQA 样本，8 任务，3 维度 | 300 对真实 A/B 测试 UI | ~1,460 合成 UI + 21 位设计师 ~1,500 条标注 |
| 数据内容 | 移动端截图 + 缺陷诊断选择题（标签经 4 位高级 UX 专家两轮校验） | A/B 胜负标签 + 专家策划的解释（含设计法则引用） | 排序对 1,098 / 评论 152 / 带包围盒批评 181 / 直接修改 68 |
| 数据可得性 | ⚠️ 仓库内**未见数据文件**（仅 cookbook 推理与评测脚本），需进一步确认获取渠道 | ✅ `WiserUI_Bench.json` 在仓库内（元数据 + 来源 URL + 标签 + 解释）；图片用脚本从原始 host 下载 | ✅ Apple CDN 直接下载 zip，四个 HF 格式数据集 |
| License | 模型 MIT；benchmark 见 LEGAL.md | CC BY-NC-SA 4.0（非商业研究） | 代码/模型/数据分设 LICENSE，数据见 LICENSE_DATA |
| 主要限制 | 任务集中在弹窗/遮挡/不一致三类现象 | 图片为第三方（GoodUI/VWO/ABTest.design）版权，不可再分发 | UI 为 LLM 合成非真实产品；评论类样本量较小 |

## 2. 逐项借用方案（映射到 skill 模块）

### 2.1 WiserUI-Bench → 条目库证据增强（M1/M2，第一优先）

**能借什么**：每条记录 = A/B 两版界面 + 真实胜负 + 专家解释（引用设计法则）。这正是条目库 `sources` 里缺的 **E3 级真实案例**。

**具体做法**：

1. 筛选电商结算/表单/支付相关子集（300 对里估计数十对），按我们的视角归类
2. 为命中条目（C01 C04 C05 C06 C13 C19 等最可能有对应案例）新增 `evidence_cases` 字段：
   ```yaml
   evidence_cases:
     - source: "WiserUI-Bench #<id>（GoodUI）"
       design_fact: "A/B 两版的界面差异描述"
       outcome: "B 版胜出（真实 A/B 测试）"
       interpretation: "专家解释（含引用的设计法则）"
       strength: E3（真实行为数据，但非本设计实测）
   ```
3. Task 2 的"设计法则"分类与我们的 L1 领域（D1–D6）做映射表，检查领域覆盖缺口

**对 skill 的价值**：AI 评审时不再只说"依据 Baymard 研究"，可以说"类似改动在真实 A/B 测试中胜出/落败，机制是××"——E2 推断获得 E3 案例佐证。

**注意**：图片只存 source URL 不随库分发（遵守其数据政策）；CC BY-NC-SA 对研究用途友好，但仓库若商用需重审。

### 2.2 ml-rldf → Issue 格式金标准 + 迭代链验证（M2/M4/M5，第二优先）

**能借什么**：这是三者中**结构价值最高**的——它的数据结构几乎就是我们 Issue 记录和 M5 迭代记录的现实版本：

| ml-rldf 字段 | 对应我们的结构 |
|---|---|
| `annotation`（评论/带包围盒批评） | Issue 记录的专家范例：问题 + 理由 + **ui_anchor（包围盒）** |
| `image` + `description` | M0 任务卡输入（设计稿 + 任务描述） |
| `improvement_prompt`（由评论提炼的改进指令） | M4 的 Proposal |
| `improved_html` / `improved_image` | M5 修改后方案 |
| `userid` | 设计师个体差异（Study B 分析需要） |

**具体做法**：

1. 抽样 comment（152 条）与 sketch（181 条，带锚点）集，对照我们的 `issue-record.md` 模板做**格式差异分析**：专家批评里哪些字段我们缺、哪些我们多出来的字段专家从不写（多出来的字段要论证存在价值）
2. 用"原始 UI → 标注 → 改进后 UI"链验证 M4：把我们的 QOC/Proposal 生成跑在同样的原始 UI 上，与设计师真实的 improvement_prompt 对比
3. ranking 集（1,098 对偏好）可作为"两条修改建议哪个更优先"的排序校准参考

**对 skill 的价值**：M2 输出格式从"自说自话"变为"与专家表述对齐"；M4 的方案生成有了可对照的真实改进链。这也是 Study A 之外又一层免费验证。

**注意**：UI 是合成的，问题分布与真实电商结算页不同（借格式与链路，不借问题分布）；Apple 的 LICENSE_DATA 需在使用前通读确认条款。

### 2.3 UXBench / UI-UX → E1 硬检查 + 专项诊断引擎（M2，第三优先）

**能借什么**：8 个缺陷任务全部是**视觉证据可确定性判定**的：

| 维度 | 任务 | 缺陷 |
|---|---|---|
| 可用性 | BubbleOcclT / BubbleOcclBtn | 浮层遮挡文本 / 遮挡可点元素 |
| 效率 | PopupNoClose / PopupBlock / PopupStack | 弹窗无关闭控件 / 挡原生关闭钮 / 多弹窗叠加 |
| 可信 | MismatchBadge / MismatchContent / MismatchFunc | 徽标 / 名称 / 功能描述不一致 |

**具体做法**：

1. 8 个任务转成条目库的 **E1 级机检条目**（挂到 D6 技术与交互状态下）——判断结果可以是确定性的"存在/不存在"，正是当前条目库完全缺失的类型
2. 他们的开源 4B 模型（HF: `afx-team/UI-UX`，MIT，vLLM 可本地部署）作为 M2 的**专项诊断引擎**：E1 机检交给它，E2 推断留给通用多模态模型——形成分工
3. 其"选择题 + 确定性输出"的提示格式（`$\boxed{X}$` 精确匹配）可借为我们 E1 条目的输出契约
4. 3 维度分类（可用性/效率/可信）与 L1 领域的对应关系写入 `domains.md`

**对 skill 的价值**：评审包里出现"弹窗未提供关闭控件（E1，机检确认，违反 ××）"这种零水分的硬结论，可信度立刻不同。

**注意**：数据集本身在仓库中未见直接下载（可能需联系作者或从 HF 获取），借用以任务定义 + 开源模型为主；场景以移动端为主。

## 3. 借用优先级与理由

| 优先级 | 数据集 | 理由 | 立即可做 |
|---|---|---|---|
| **1** | WiserUI-Bench | JSON 元数据就在仓库，零门槛；直接增强条目库证据，见效最快 | 筛选电商子集 → 写 `evidence_cases` 字段进条目 |
| **2** | ml-rldf | 数据可下载；结构上是 Issue/迭代记录的现实原型，格式校准价值独特 | 下载 comment/sketch 集 → 做格式差异分析 |
| **3** | UXBench | 主要借任务定义与开源模型；数据可得性待确认 | 8 任务转为 E1 机检条目（不依赖其数据） |

三者的借用互不冲突：WiserUI 喂**依据**，ml-rldf 校**格式**，UXBench 补**硬检查**。

## 4. 许可合规清单

## 5. 与研究计划的衔接

- `evidence_cases`（WiserUI）= Study A 的 M2 评测参照之一
- 格式差异分析（ml-rldf）= Issue Schema v0.2 修订输入
- E1 机检条目（UXBench）= M2 新增"确定性检查"子流程，且天然可复现（回归测试友好）
