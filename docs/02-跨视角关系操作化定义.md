# 跨视角意见关系操作化定义（v0.1）

> 配套文档：`01-评价条目库Schema与录入规范.md`（Issue 记录 Schema 是本文的分析对象）
> 用途：M3/P4 关系引擎的判定规范 + Study A 的标注指南
> 状态：七种关系与判定流程已定义；正反例需经双人标注校准

---

## 1. 分析对象：六字段结构化比较

关系分析**不比较自由文本**，只对 Issue 记录的以下字段做结构化比较：

```
ui_anchor（评价对象） + observed_fact（设计事实） + evidence_basis（评价依据）
+ evaluation_goal（目标） + proposed_change（建议） + 证据状态（E 级 + verification_status）
```

跨页面 / 跨状态的意见对另附 `task_step_id` 或 `transition_id`（如「切换支付方式」→「返回后订单状态丢失」），用于语境对齐（见 §3 Step 0.5）。

## 2. 三层分析框架

| 层 | 判断什么 | 用的字段 |
|---|---|---|
| 事实层 | 两条记录对界面的观察是否一致 | `ui_anchor` + `observed_fact` |
| 策略层 | 两条修改建议能否同时实施 | `proposed_change` |
| 目标层 | 修改是否导致目标间此消彼长 | `evaluation_goal`（+ 共享资源判断） |

## 3. 判定流程（决策树）

```
Step 0  对象锚定
        无共享 UI 对象且无共享任务步骤
          → 无关系（independent），不进入后续分析
Step 0.5 语境对齐（2026-11-03 新增，前置）
        核对方案版本 / 任务步骤（task_step_id / transition_id）/ 界面状态 / 适用人群（applies_to）
        任一项不匹配
          → Conditional（人群或状态不同、各自条件内成立）
          → 或暂缓判定（版本不一致时先统一输入，不得带着版本差直接判定冲突）
Step 1  事实层
        observed_fact 直接冲突（无法同时为真）
          → Contradiction：触发 E1 核查
              核查解决 → 关闭并记录；未决 → 降级 Uncertain
        事实一致 且 问题判断同向、指向同一问题
          → Support
Step 2  策略层
        建议互斥（一个移除另一个的作用对象）
          → 转 Step 3 判断是否真权衡
        建议存在先后 / 包含关系
          → Dependency
        建议兼容
          → 转 Step 3
Step 3  目标层
        共享有限资源（注意力 / 屏幕空间 / 信息密度 / 操作步骤 / 时间）
        且能写明损害机制（「改动 X 改善目标 A，同时通过 ×× 机制损害目标 B」）
          → Trade-off
        仅资源竞争推测、无损害机制路径
          → Uncertain（待验证，不判 Trade-off）
        共享改进目标 且 协同
          → Complement
Step 4  兜底
          → Uncertain（必须附缺失证据清单）
```

**输出允许双字段**：`primary_relation`（主关系）+ `resolution_path`（化解路径）。许多 Trade-off 的化解路径正是条件化设计（见 C04/C05 例）。

## 4. 七种关系的操作化定义

### 4.1 Support 支持

- **定义**：不同条目对同一设计问题给出方向一致的判断，可互相印证。
- **必要条件**：① 锚定同一 UI 对象或任务步骤；② 问题判断同向；③ 无事实分歧。
- **层级**：事实层一致 + 判断层一致。
- **正例**：C06-01（金额明细被折叠）与 C13-01（支付按钮与金额层级混乱）都指向"最终金额核对负担"→ 合并为一条 Issue，证据来源记两条目。
- **反例（不是 Support）**：C03-01 与 C09-01 都说"表单有问题"，但一个是字段数量、一个是必填标识——问题判断不同，应为 Complement。
- **处理**：合并证据，问题优先级上升（多来源独立支持）。

### 4.2 Contradiction 反驳

- **定义**：两条记录对同一界面事实给出不一致的观察。
- **必要条件**：① 锚定同一对象；② `observed_fact` 直接冲突；③ 无法同时为真。
- **层级**：事实层。
- **正例**：C06-01 记录"运费在当前状态不可见"，C08-01 记录"配送费用已展示"——同一区域的事实冲突。
- **反例（不是 Contradiction）**：C04-01"优惠入口难以发现" vs C05-01"优惠输入框干扰注意力"——两个不同观察，不构成事实矛盾（这是最常被误标为冲突的情形）。
- **处理**：触发 E1 核查（截图 / Figma 属性）；核查后保留正确一方，未决则降级 Uncertain。

### 4.3 Complement 互补

- **定义**：针对不同问题的建议可协同实施，共同改善一个共享目标。
- **必要条件**：① 对象 / 问题可以不同；② 建议互不冲突；③ 存在共享的改进目标。
- **层级**：策略层兼容 + 目标层协同。
- **正例**：C07（优惠应用后反馈不明确）与 C12（支付确认信息不足）——不同修改，都提升"用户对金额与状态的确定感"。
- **反例（不是 Complement）**：两个建议虽可同时实施，但争夺同一注意力资源 → 是 Trade-off。
- **处理**：合并为组合方案（一个 QOC Option）。

### 4.4 Trade-off 权衡

- **定义**：一个条目的改善可能损害另一个条目的目标（有限资源竞争）。
- **必要条件**：① 建议都可行；② 至少共享一种有限资源（注意力 / 空间 / 信息密度 / 步骤 / 时间）；③ 语境对齐通过（版本 / 步骤 / 状态 / 人群一致，见 Step 0.5）；④ 能写明损害机制——「改动 X 改善目标 A，同时通过 ×× 机制损害目标 B」。证据不足（仅有资源竞争推测）时判 Uncertain，不得因"无法证明可同时最优"而过早判 Trade-off。
- **层级**：目标层（可含策略层互斥）。
- **正例**：C04（强化优惠入口可发现性）vs C05（抑制优惠区干扰）——争夺注意力资源；主关系 Trade-off，化解路径 = 分层 / 条件展示（Conditional 式化解）。
- **反例（不是 Trade-off）**：C13（突出支付按钮）vs C04（突出优惠入口）——看似争夺视觉层级，但若两者不在同一视觉区域且层级有主次安排，不构成必然权衡 → 应归 Conditional 或 Complement，需先检查布局约束（这正是"防伪造冲突"第 3、4 问的作用）。
- **处理**：转 QOC；**先检查是否存在兼顾结构**（分层 / 条件展示 / 按需展开），存在则把兼顾方案记为候选 Option，且不得直接宣布"某视角获胜"。
- **方案空间重构原则**（2026-11-03 确认）：AI 不应只在既有 A / B 两个方案中选择——化解 Trade-off 时应尝试利用不同视角的有效信息重组方案空间（"分层展示"即 A 与 B 的结构重组，而非各退一步的折中）。最终输出可以不是绝对排名，例如"推荐验证 C，同时保留 A 作为对照"，并附依据与不确定性。

### 4.5 Dependency 依赖

- **定义**：一条修改的实施顺序或效果依赖另一条先完成。
- **必要条件**：① 建议间存在先后或包含关系；② 顺序颠倒导致返工或失效。
- **层级**：策略层。
- **正例**：C10（错误提示需定位到具体字段）依赖 C09（必填标识清晰）先落地，否则错误定位指向不明。
- **反例（不是 Dependency）**：两条建议只是"都该做"、无顺序约束 → Complement。
- **处理**：生成实施顺序，依赖链写入 QOC 的实施约束。

### 4.6 Conditional 情境差异

- **定义**：两条判断分别适用于不同用户群、任务意图或界面状态，在各自条件下都成立。
- **必要条件**：① `applies_to` / 适用条件字段不同；② 各自条件内均成立。
- **层级**：跨层。
- **正例**：C04-01 对"有优惠需求的用户"成立（入口难发现），C05-01 对"无优惠需求的用户"成立（输入框干扰）——不是冲突，是两个子人群的不同问题。
- **反例（不是 Conditional）**：两个判断表面针对不同人群，但其中一个的条件实际不成立（如所有用户都必经该状态）→ 需重新归类。
- **处理**：条件化设计（分层展示、按需展开）；条件写入 QOC 的 Criteria；`applies_to` 回填到设计约束。

### 4.7 Uncertain 不确定

- **定义**：现有证据状态不足以判定关系。
- **必要条件**：① 无法通过 Step 0–4 闭合判定；② **必须记录缺失的证据项**。
- **正例**：C05-01 的干扰效应是否真实存在需 E3 数据（完成时间对比），数据缺失期间标记 Uncertain。
- **反例（不是 Uncertain）**："AI 不确定哪条对"而无缺失证据清单——禁止作为偷懒出口。
- **处理**：保留判断并生成验证任务，进入 E3 验证队列。

## 5. 关系记录 Schema

```yaml
relation_id: REL-001
record_pair: [C04-01, C05-01]
primary_relation: Trade-off          # 七选一
analysis_layer: 目标层                # 事实 / 策略 / 目标
judgment_basis:                      # 引用具体字段值，禁止只写语义相似
  - "共享资源：注意力（订单确认页主任务路径）"
  - "C04 evaluation_goal=降低优惠查找成本；C05 evaluation_goal=保障结算连续性"
resolution_path: 条件化分层展示        # 化解路径（如适用）
verification_status: 待核实
action: 转 QOC                        # 合并 / 核查 / QOC / 排序 / 条件化 / 生成验证任务
```

## 6. 与"防伪造冲突四问"的对应

| 原四问（方案 v1） | 现落地为 |
|---|---|
| 两条意见是否指向同一对象或流程？ | Step 0 对象锚定 |
| 是事实矛盾、方案互斥还是目标张力？ | 三层分析框架（Step 1–3） |
| 冲突在当前约束下是否真实存在？ | Trade-off 必要条件③（约束检查） |
| 能否通过重组界面同时满足两个目标？ | `resolution_path` 字段 |

## 7. Study A 标注与校准建议

1. **优先标注边界案例**：Trade-off vs Conditional、Support vs Complement 是最易混淆的两对；每对准备 5+ 个金标准判例。
2. **双人独立标注 + 分歧裁定**，报告一致性系数（Cohen's kappa）；关系判定指南随分歧案例持续修订。
3. **建立 20–30 个"金标准关系对"**（含正反例），作为 M3 关系引擎的回归测试集——每次 prompt 或模型变更后重跑，防止关系分类质量漂移。
4. 与条目库联动：发现某条目反复产生 Uncertain，优先检查该条目的 `evidence_requirements` 是否缺失 E1 最低证据。
