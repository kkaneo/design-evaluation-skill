## 1. 三层结构与一个关键设计决定

```
L1 评价领域（跨 UI 类型复用，D1–D6）
 └─ L2 任务化视角（针对当前任务的问题组，动态生成）
     └─ L3 评价条目（可执行检查单元，本 Schema 定义的对象）
```

**关键设计决定（已确认 2026-11-03）：L2 不是手工封装的固定模块，而是"L3 条目 × 任务目标 × 适用情境"的动态映射结果。电商结算不预设固定 L2 视角；若现有条目覆盖不足，AI 可生成新维度候选，最终确认权在设计师。**

每次评审时，系统按任务语义检索 L3 条目，再按共享评价目标聚类为若干 L2 视角，交设计师确认。同一 L3 库在不同任务下生成不同的视角组合——这正是"任务自适应"的机制载体，也是与 naive 检索（只选不组装）形成差异、需要在评测中演示的核心点。

条目 Schema 中的 `applicable_context` 与 `evaluation_goal` 字段是动态组装的两个键：前者决定检索命中，后者决定聚类归属。

### 动态组装闭环（含 AI 生成新维度）

```
任务输入（设计任务卡）→ 检索命中 L3 条目 → 按 evaluation_goal 聚类为 L2 候选视角
→ 覆盖检查：任务目标是否被现有条目覆盖？
   覆盖不足 → AI 生成新维度候选（必须登记溯源）
→ 设计师确认 / 删除 / 补充 → 形成本次评价清单
```

AI 生成新维度的三条纪律（防止新的幻觉面）：

1. **溯源必填**：新维度必须写明依据来源（文献 / 规范 / 或明确标注"AI 补充，待专家校准"），与 L3 条目同等级的 provenance 要求，禁止无依据的"新视角"；
2. **入库需确认**：AI 生成的新维度默认仅在本次评审使用；要沉淀为正式条目，必须经设计师确认后按本 Schema 补全全部字段；
3. **全程留痕**：每次生成的新维度与确认结果记入评审日志——这既是审计依据，也是未来 Study A"必要视角覆盖率 / 无关视角比例"指标的数据来源。

### 组装机制验收用例（来自项目头脑风暴，2026-11-03）

动态组装机制实现后，以下任务卡应产出对应的视角配置（作为单元 / 回归测试用例）：

| 任务卡（优化目标 + 用户） | 期望生成的视角 | 期望被过滤的内容 |
|---|---|---|
| 提高首次购买用户的结算完成率 | 任务效率、注册阻碍、费用透明、转化 | 品牌视觉细节 |
| 优化老年用户的结算体验 | 信息理解、认知负荷、无障碍、错误预防 | 复杂的个性化推荐策略 |
| 提高优惠券使用率 | 优惠可发现性、优惠规则理解、转化、干扰成本 | 非关键的页面微动效 |
| 降低订单支付错误率 | 订单核对、风险提示、错误恢复、交易确认 | 营销内容曝光 |
| 评审整个结算流程改版方案 | 任务流程、业务目标、认知体验、视觉层级、风险控制 | 视实际约束进一步筛选 |

说明：期望输出允许合理的条目差异（视角名称不必逐字匹配，`evaluation_goal` 聚类归属一致即可）；"期望被过滤"列用于检验 out_of_scope 过滤与无关视角比例。这组用例同时是"任务自适应"最直接的演示材料。

## 2. L3 条目 Schema

### 字段定义

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✓ | 唯一标识（如 `C05`），Issue 记录以此溯源 |
| `name` | ✓ | 条目名 |
| `version` | ✓ | 版本号（专家校准后递增） |
| `domain` | ✓ | L1 归属：一个主域 + 0–2 个副域 |
| `perspective` | ✓ | 默认 L2 归属；动态组织时可被重组 |
| `applicable_context` | ✓ | 适用情境：页面类型 / 用户任务 / 用户状态 |
| `evaluation_goal` | ✓ | 本条目希望优化的体验或业务结果（聚类键） |
| `check_questions` | ✓ | 2–4 个具体检查问题，防止泛泛评价 |
| `judgment_rules` | ✓ | `problem_if` / `not_a_problem_if` / `severity_conditions` |
| `sources` | ✓ | 来源列表：具体主张 + 证据强度 + 可访问性说明 + 核验状态 |
| `evidence_requirements` | ✓ | E1 最低证据清单；缺少何种证据不能下结论 |
| `boundaries` | ✓ | 本条目**不能**推断什么（与 `problem_if` 同等必填） |
| `output_contract` | ✓ | 输出遵循 Issue 记录 Schema（见第 3 节） |
| `validation_needs` | ✓ | E3 验证指标，必须可被 Study C 事件 schema 采集 |
| `real_world_cases` | 可选 | 真实产品案例（E1 界面事实 + E2 推断），作为判断规则的现实锚定 |

### 完整示例

完整 YAML 示例与全部正式条目（C05、C15–C20）统一维护于 `../knowledge/criteria/`——首个完成全字段的条目是 C05（优惠信息干扰，见 `C05.yaml`）。本文件不保留条目副本，避免双处维护产生版本漂移。

## 3. Issue 评价记录 Schema（M2/P3 输出契约）

| 字段 | 说明 | 服务于 |
|---|---|---|
| `issue_id` | 如 `C05-01`（条目号 + 序号） | 追溯 |
| `criterion` | 来源条目 id | 追溯 |
| `ui_anchor` | Frame 名 + 区域 + 元素，尽量精确到节点 | **关系分析第一聚类键** |
| `observed_fact` | 可观察事实，标注 E1 并注明是否已核实 | Contradiction 判定 |
| `evidence_basis` | 评价依据（引用条目来源的具体主张） | Support / 证据核查 |
| `judgment` | 问题判断（按第 4 节动词规范措辞） | 事实层关系判定 |
| `proposed_change` | 修改建议 | 策略层关系判定 |
| `applies_to` | 适用条件（用户状态 / 意图） | **Conditional 判定依赖（新增关键字段）** |
| `evidence_type` | E1 / E2 / E3 | 证据分级 |
| `verification_status` | 已核实 / 待核实 / 证据矛盾 / 无法判断 | 独立于 E 级的状态追踪 |
| `validation_needs` | 待验证指标清单 | 进入 E3 验证队列 |

可直接填写的运行时模板见 `../templates/issue-record.md`。

## 4. 录入规范

1. **来源登记四要素**：具体主张（哪项研究、说了什么）+ 证据强度（E1 规范 / E2 研究发现 / E3 实证）+ 可访问性说明 + **核验状态**（已核对原文 / 待核实）。禁止只贴链接。
   **二手引述规则（2026-11-03 确认）**：转述他人研究的来源（博客引用 Baymard 等）默认标 `待核实`——二手来源只是提供视角与方向的参考，其情境与被评审场景不完全符合，因此**不单独支撑 `problem_if` 判定**；核对原文后方可升格为正式依据。
2. **边界必填**：`not_a_problem_if` 与 `boundaries` 不填视为条目未完成——边界写"不能结论什么"与"能结论什么"同等重要。
3. **适用条件显式化**：`applicable_context.user_states` 与 Issue 的 `applies_to` 必须显式写出，Conditional 关系判定完全依赖此字段。
4. **措辞三级动词**（防止证据越级）：
   - E1 事实：「未呈现」「违反 ×× 规则」「与 ×× 不一致」
   - E2 推断：「可能增加 / 降低 ××」「存在 ×× 风险」
   - E3 断言：未经实测**禁止**出现效果结论；只能写「需验证」「预计影响 ××（待 E3）」
